Evolutionary Algorithm Benchmark Selection System

Describe your optimisation problem in plain words. The system finds the closest benchmark problem in a knowledge base mined from conference papers, tells you how sure it is, and lists the evolutionary strategies that were reported on it.

Objectives

What the project sets out to do

Build the knowledge base

Turn results scattered across paper PDFs into one searchable table of benchmark problems, landscapes, algorithms and reported outcomes.

Match a problem to a benchmark

Take a user's plain-language description and find the closest known problem, instead of asking for exact function names.

Rank strategies by evidence

For each problem, list the strategies reported on it, grouped by performance metric and ordered by how much evidence supports them.

Be honest about confidence

Report how sure the match is separately from how many papers back the answer, and decline to answer when the match is weak.

Grow beyond text

Return the right benchmark and its standard datasets to EvoLabs, the application that runs the algorithms, and add matching on the measured shape of the user's objective function (landscape analysis).

Problem statement

Choosing an evolutionary algorithm is still mostly guesswork

Hundreds of papers report how evolutionary algorithms perform on benchmark problems. Someone with a new problem has to read many of them, work out which benchmark resembles their own, and guess which results transfer.

The evidence exists, but it is locked in PDFs written in different styles. This project reads it once, structures it, and makes it queryable, so the question "what has worked on problems like mine?" gets an answer with its supporting evidence attached.

  • Same problem, different words.One benchmark appears under many names and spellings, so papers cannot be grouped by title alone.
  • Metrics do not compare.A mean error and a success rate cannot be ranked against each other, so strategies are ranked per metric only.
  • Missing details.Many papers leave out parameters such as population size; where we fill in a standard default, it is treated as a default, not as a finding.

Where this fits

Algorithm selection

Rice's framework maps problem features to the algorithm expected to do best. For continuous problems the features usually come from Exploratory Landscape Analysis (ELA), which needs samples of the objective function. This system works one step earlier, from a description, and uses the literature as its labelled library.

Benchmarking platforms

COCO and IOHprofiler standardise benchmarking, and DEAP, jMetal and pymoo provide algorithm implementations. They expect the user to name the benchmark and do not explain why a benchmark suits a real problem.

Extraction and retrieval

Large language models can extract structured records from scientific text when held to a schema; this project uses Gemini. Search combines BM25, dense sentence embeddings, reciprocal rank fusion and cross-encoder re-ranking.

Methodology

From a paper PDF to a ranked recommendation

The pipeline runs in eight stages. Each stage writes a file the next one reads, so every result can be traced back to the papers behind it.

  1. 1

    Extract LLM + fixed schema

    A language model reads each paper and fills a fixed set of fields: problem, landscape traits, algorithm, parameters, performance metric and outcome.

  2. 2

    Clean Python · Pandas

    Placeholders are standardised, duplicate records removed, and unreported numeric parameters set to standard defaults that stay marked as defaults.

  3. 3

    Describe each record

    One matching text is built per record: function name and landscape for benchmark papers, problem context and title for applied papers. Non-English text is translated.

  4. 4

    Embed all-mpnet-base-v2

    Each text becomes a 768-number sentence embedding, so descriptions with similar meaning sit close together.

  5. 5

    Group into problem entities name keys + clustering

    Records that describe the same problem are merged, using name rules (for example every CEC 2017 variant) plus embedding clusters. Entities are typed as suite, single function or named subset. Checked against a hand-labelled set of 38 papers.

  6. 6

    Rank strategies

    For each entity, strategies are ranked within each metric family, never across metrics, ordered by whether the optimum was found, how often, and how many papers report it.

  7. 7

    Match a user's query BM25 + dense + cross-encoder

    Keyword search and embedding search each return candidates; reciprocal rank fusion merges them; a cross-encoder re-scores the shortlist, with a small bonus for entities backed by more papers.

  8. 8

    Answer with confidence

    The output gives the matched entity, a match confidence (the margin between the top two candidates), the evidence strength (papers behind it) and the strategies by metric. If the margin is too small, the query is logged as unmapped.

Data

From conference papers to structured records

Whole papers are read by a language model into a fixed, validated schema, one record per algorithm and benchmark pair. The dataset names they report are then sorted into tiers so they can be counted.

Extraction procedure

  • Whole papers. Each PDF is uploaded whole to the Gemini File API and processed in one call at temperature 0.1, which keeps result tables, experimental settings and problem definitions together.
  • No guessing. The prompt asks for null wherever the paper states nothing, a synthetic-benchmark or real-world label for each study, one entry for every algorithm and benchmark pair, and fixed rules for modality and separability.
  • Schema-checked. A Pydantic model is passed as the response schema, so malformed output is rejected before it is stored.
  • Robust batches. The batch processor skips papers already extracted, so interrupted runs resume; it rate-limits requests, retries with exponential back-off, rotates API keys when quotas run out and writes a report per run. Unit tests cover valid, invalid and round-trip cases for every schema model.
  • One row per pair. The nested answer is flattened into a 27-column table: a paper testing four algorithms on six problems gives 24 rows. The year of a PDF's folder overrides the year the model reads from the paper.

Dataset and domain classification

Free-text dataset names vary widely, so a rule-based classification makes them countable. It works in four tiers, each an ordered list of regular expressions where the first matching rule wins.

TierWhat it captures
1Datasets used by two or more papers, counted per distinct paper and split into Applied and Theory use.
2Datasets used by a single paper, grouped into 12 benchmark families (CEC, BBOB/COCO, DTLZ, ZDT, WFG, TSP/routing, program synthesis, image, OpenML/UCI, classic functions, RL environments, custom/simulated) plus a residual “Other / domain-specific” class.
3The residual class split into program-synthesis benchmarks, bit-string/Boolean problems, RL/game environments, problem-instance libraries, opaque labels, pure-math test functions and genuine real-world datasets.
4The application domain of each paper, from its problem context: 12 domains (for example routing and logistics, scheduling, classification and detection) plus “Other applied” and “Pure math / theory”.

First run on GECCO 2020–2026: 767 papers classified as 390 Applied and 377 Theory. A manual audit of the 2020 residual class found about 157 of its 298 datasets were genuine real-world data and about 75 were synthetic test functions the Tier 2 rules missed (spelling variants such as “Griewangk”, suites such as YABBOB), so the Tier 3 rules were extended.

Corpus

Five venues consolidated into one cleaned corpus

The combined input held 11,703 records. Its fields were complete, but it had five classes of defect, which a deterministic, re-runnable cleaning script fixes while logging every change.

Defects found

  • Paper IDs restarted every year and collided across venues (5,701 repeated IDs).
  • Missing values were written two ways, “Unknown” and “Not Reported”.
  • 114 PReMI records used an undefined category, “Benchmark”.
  • Some papers appeared more than once: GECCO 2020 papers copied into the 2026 folder, cross-venue copies, and PReMI papers stored up to six times under different years.
  • The GECCO 2024 block came from an export made before twelve papers had been extracted.

Cleaning procedure

  1. Complete GECCO 2024 from the stored JSON extractions with the pipeline's own flattener (88 records).
  2. Remove duplicate papers by normalised title: GECCO 2020/2026 copies keep the copy with more records and are relabelled 2020; cross-venue copies go to their true venue; otherwise the copy with most records is kept. Identical records within a paper are dropped.
  3. Unify missing markers: “Unknown” and “Not specified” become “Not Reported”.
  4. Fix categories: “Benchmark” becomes “Pure Math”.
  5. Normalise numbers, for example 100.0 to 100.
  6. Issue unique IDs that encode year, venue, paper and record number (for example P2024_GECCO_012_Ext_03), keeping the original ID.

Knowledge base

From records to benchmark entities

Every record gets a short search text and an embedding; benchmark names are resolved into entities; each entity stores its aliases, evidence, disagreements and ranked algorithms.

Search text and embeddings

  • Applied records use the problem context with the paper title; Pure Math records use the benchmark name with its target landscape and reported characteristics.
  • Repeated fragments are removed and very short texts padded with further fields. On the CEC records shared with the first build, 82.2% of texts are identical.
  • Texts are encoded with all-mpnet-base-v2 into L2-normalised 768-dimensional vectors, with a SHA-256 hash per text so changes can be detected. Embedding the 11,342 records took 45 s on an Apple-silicon laptop.

Entity resolution

  • A normalised name key: lower-cased, spelling variants unified (“salesperson” to “salesman”, “travelling” to “traveling”), generic words such as function, benchmark, suite and test dropped.
  • Names mentioning a CEC competition year map to a suite key (“cec_2017”), and “Long Name (ACR)” merges with “Long Name” when that key exists in the same category.
  • Agrees with the first build's grouping on 99.4% of names. In kb-v2 it turns 3,374 distinct names into 3,100 groups; 145 records merged through acronyms and 809 records fall into 17 CEC suite entities.

Entity records

  • The medoid record, the member most similar to all others, supplies the base description:
    mb = argmaxi∈b Σj∈b, j≠i vi⊤vj
  • Descriptions start with the canonical name, Pure Math descriptions gain every member's landscape traits, and eleven artefact entities (an algorithm name in the benchmark field) are removed.
  • Confidence tiers: high for 5 or more supporting papers, medium for 2–4, low for 1. Disagreements on modality, separability, landscape or dimensionality are stored, not voted away; DTLZ1, DTLZ2, … are linked as variant families.

Query flow

How a query is answered

What happens between typing a description and seeing recommended strategies. Values are the defaults in the repository's retrieval and output scripts and match the search figure in the progress report.

A
Stage A

Understand the query

  1. User textA plain-English description of the optimisation problem.
  2. Keyword searchBM25 (k1 = 1.5, b = 0.75) · finds entities that share the query's words; strong on exact names such as “ZDT1”. Returns 20 candidates.
    Meaning searchall-mpnet-base-v2 embeddings · finds entities with a similar meaning, so “many local minima” still reaches Rastrigin. Returns 20 candidates.
B
Stage B

Match to a problem

  1. Reciprocal rank fusionMerges the keyword, meaning and paper-count rankings into one list (k = 60). Only positions are combined, because the rankers' scores have different scales.
  2. Shortlist of 10Only the ten best merged candidates go forward.
  3. Cross-encoder re-scorecross-encoder/ms-marco-MiniLM-L-6-v2 reads the query and each candidate together, then adds a small bonus for entities backed by more papers: score + 0.5 × ln(1 + papers). One paper adds 0.35 and 25 papers add 1.63: enough to settle close calls, not enough to overturn a clearly better match.
  4. Margin checkThe top candidate must beat the second by at least 1.0. Cross-encoder scores have no fixed scale, so the gap is tested, not the score.
  5. passMapped problem entityThe match goes on to Stage C.
    failNot mapped: logged for reviewNo answer is forced; the query is saved for the team.
C
Stage C

Recommend

  1. Look up the strategy tableReads the matched entity's rows from the ranked strategy layer.
  2. Group by metric familyResults reported under different metrics are never compared.
  3. Rank within each familyFirst by whether the optimum status was reported, then by the share of reports where the optimum was found, then by papers reporting.
  4. OutputThe entity, match confidence (the margin), evidence strength (papers and description confidence), the landscape properties papers disagree on, and up to 3 metric families × 5 strategies each. Keeping the two confidences apart stops “unsure which problem you mean” from looking like “well understood but rarely studied”.

Evaluation

How well the search works

The search was evaluated on 20 held-out plain-language descriptions: 8 easy ones describing a well-known benchmark, 6 hard ones (4 scorable, 2 deliberately ambiguous and not scored) and 6 out-of-scope ones, such as recipes, travel plans and tax returns, that should be refused. A query counts as correct when the system returns the expected entity or, for out-of-scope queries, when it refuses. This evaluation ran on the first knowledge base, kb-v1; for kb-v2 the test set has been re-mapped to the new entity IDs, but the full evaluation has not been run yet.

Of the 12 scorable in-scope queries the system answered 7 and was right on 5, so when it answered it was right 71% of the time; it refused the other 5. The 61% in Progress counts the 6 refused out-of-scope queries as correct too (11 of 18 scored queries).

What the run showed

  • All out-of-scope queries were refused, with a largest margin of 0.22, well below τ = 1.0.
  • Mean margins were 3.47 for correct answers and 0.89 for incorrect ones.
  • A OneMax description was answered with the artefact entity “Multifactorial Evolutionary Algorithm (MFEA)” at margin 3.09. This led to the artefact filter, and that entity no longer exists in kb-v2.
  • A LeadingOnes description returned the related “Generalized Leading-Ones” entity.
  • Most refusals were on multi-objective benchmarks (ZDT1, ZDT3, ZDT4, DTLZ1), where several single-paper entities describe similar Pareto fronts.

Behaviour of the current knowledge base

Descriptions run against kb-v2 with the real models. Well-described problems are answered with large margins; the multimodal description now reaches Rastrigin backed by 25 papers instead of 11. Short descriptions naming common problems are refused.

Failure analysis

The refused TSP description has the highest top score of all, so it is not a weak match. TSP is represented by two entities with the same name key, one Pure Math (7 papers) and one Applied (5 papers), because names are grouped within each category, plus about 44 further TSP-related entities at instance level. Two near-identical candidates always produce a small margin, so the refusal rule fires on the problems the system knows best. Similarly, 41 entities contain “Sphere” in their name, including “Sphere (f1)” and “BBOB f1 (Sphere function)” next to the 29-paper “Sphere function”. The refusal rule therefore depends on complete entity resolution.

Limitations

  • Extraction accuracy is not yet measured: the schema rejects malformed values but cannot catch a wrong value of the right type.
  • Imputed fields: unreported numeric parameters were filled with documented defaults and must not be read as evidence; half the records do not report modality.
  • Coverage: PPSN was extracted from whole volumes, EvoStar is not yet included, 24 GECCO 2026 papers are not yet extracted, and some PReMI records describe non-evolutionary methods.
  • Strategy ranking: most records report no outcome, so 1,320 of the 1,875 entity–metric groups with several algorithms fall back to alphabetical order.
  • Rule-based classification: the Tier 2–4 rules miss spelling variants, and the default Tier 3 class still mixes real-world datasets with test functions.
  • Evaluation scale: twenty queries expose failure modes but are too few to tune α and τ.
